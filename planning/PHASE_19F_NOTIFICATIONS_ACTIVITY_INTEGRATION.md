# Arc 19F — Notifications & Activity Integration

## Status

**Complete** — Lightweight operational awareness routing, notification center foundations, read state, relevance aggregation, preference scaffolding, and deferred digest placeholders.

---

## What Was Built

### Schema foundations

Arc 19F adds five notification-domain models on top of the Arc 19A–19E entry, activity, graph, and workflow foundations:

- `AwarenessEvent` — immutable awareness-generation record for relevant operational changes
- `Notification` — aggregated, organization-scoped in-app awareness item keyed by relevance subject
- `NotificationReadState` — per-person read/unread state for a notification
- `NotificationPreference` — per-person per-organization relevance and delivery foundations
- `NotificationDigest` — deferred digest placeholder for future channel delivery windows

New enums:

- `AwarenessEventType`
- `NotificationCategory`
- `NotificationDeliveryTiming`
- `NotificationDigestStatus`

### Runtime services

`lib/notifications/` now provides:

- awareness generation for entry activity, workflow changes, attendance review, and event status changes
- recipient and visibility resolution using organization/program/team staff scope plus direct assignment context
- aggregation keyed by operational subject (`Notification.aggregateKey`) to avoid repeated spam
- per-person preference filtering and minimum-priority filtering
- read/unread state mutation helpers
- pending digest placeholder queuing for `DIGEST_ONLY` preferences
- live due/overdue awareness queries for assigned work

### UI

A lightweight notification center now exists at `/notifications`.

It includes:

- unread/all awareness views
- mark read / mark unread / mark all read handling
- live due/overdue awareness lane
- preference foundations
- lightweight deferred-delivery messaging
- sidebar unread badge

### Hook integration

Awareness generation now routes through operational mutations already established in earlier arcs:

- `writeEntryActivity()` in both `lib/entries/service.ts` and `lib/operational-entry/service.ts`
- workflow step/run activity writes in `lib/operational-workflow/service.ts`
- follow-up chain activity writes in `lib/operational-workflow/chain.ts`
- operational graph entry-link activity writes in `lib/operational-graph/service.ts`
- follow-up task create/update routes through their synchronized entry activity writes
- attendance capture route
- event status update route

## Awareness Architecture Decisions

### 1) Awareness events stay separate from entry activity

`EntryActivity` remains the canonical audit/activity stream for entries. `AwarenessEvent` is a derived operational-awareness layer used only when an activity is relevant enough to route to people. This keeps notifications lightweight and prevents every activity record from becoming user-facing noise.

### 2) Notifications aggregate by operational subject, not by raw event count

`Notification.aggregateKey` collapses repeated updates about the same assignment, readiness item, workflow run, linked issue, or event into one evolving awareness item. The notification center stays calm because repeated state changes update an existing notification instead of generating a long unread list.

### 3) Read state is per-person, not global

`NotificationReadState` stores recipient-specific read/unread state. A shared operational notification can be relevant to multiple staff members without forcing a shared read state or duplicating the entire notification payload per user.

### 4) Visibility is organization-scoped but relevance-aware

Everything remains organization-scoped in storage, but recipient routing is narrowed using direct assignee/creator context and team/program/org staff scope. This preserves operational visibility while avoiding broad-feed behavior.

### 5) Due awareness is live, not scheduler-driven

Due/overdue awareness is queried live from open assigned entries rather than generated by a scheduler. This keeps Arc 19F lightweight while still surfacing operational urgency without introducing cron, push, or reminder infrastructure.

## Relevance Rules

Notifications are generated only for awareness categories that map cleanly to operational work:

- assignment updates
- follow-up creation
- readiness issue activation
- workflow step/run attention
- linked operational issue changes
- attendance needing review
- event status changes

Noise-reduction rules:

- actor is excluded from recipient routing when possible
- aggregation collapses repeated changes on the same subject
- preferences can mute categories entirely
- minimum-priority filtering suppresses low-value items
- due/overdue awareness is shown in its own lane instead of inflating unread counts

## Deferred Delivery Scope

Arc 19F intentionally does **not** build:

- email delivery
- SMS delivery
- push notifications
- realtime sockets
- background reminder schedulers
- multi-channel delivery orchestration
- escalation automations

What *is* included for future delivery compatibility:

- `NotificationPreference.deliveryTiming`
- `NotificationDigest` placeholder records grouped by digest windows
- stable awareness categories and aggregate keys
- per-recipient read state and preference foundations

This creates a clean handoff for a future delivery arc without forcing CadreOS into enterprise notification-engine behavior now.
